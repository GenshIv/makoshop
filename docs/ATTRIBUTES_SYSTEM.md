```

      без документа:         1 407   (полные сироты)
```

Разбивка 6 298 "данных без реестра":
- **3 049** кодов есть в EAN-страницах — значит последняя пересборка индексов
  (`/admin/rebuild-attrdef-indexes`) была выполнена **до** последнего импорта;
- **3 249** кодов есть только в товарах и **ни в одной EAN-странице**.

**Причина 1 (устаревший реестр)**: `attrdef_list` пополняется только
`RebuildAttrValuesFromEANPages` (union по кодам EAN-страниц) и
`BatchGetOrCreateByKeys` (union по новым ключам импорта). Коды, которые
появились в товарах после последней пересборки, в список не попадают.
(`BatchUpsertCodes` с перезаписью списка — мёртвый код, нигде не вызывается.)

**Причина 2 (устаревшие EAN-страницы)**: EAN-страницы сильно отстают от товаров.
Факты из базы:
- товар `Electrolux EWUS040B8B` (EAN 7332543813407) имеет **39 атрибутов**,
  а его EAN-страница (`eanpage:539637`) — **1 атрибут**;
- у товара с EAN 7332543813094 EAN-страницы **нет вообще**;
- суммарно 5 570 кодов товаров отсутствуют во всех EAN-страницах.

Вероятная причина: при полном реимпорте (2 сентября, `workers=8`) параллельные
импорты компаний делают `mergeAttributes` в одну и ту же EAN-страницу без
координации (race condition → lost updates), либо импорт был прерван до фазы
пересборки EAN-страниц.

## 2. Корневые причины

1. **Реестр и EAN-страницы устаревают относительно товаров**:
   - `attrdef_list` пополняется только пересборкой по EAN-страницам /
     батчем новых ключей импорта — коды, появившиеся в товарах позже,
     в реестр не попадают;
   - EAN-страницы не пересобираются после каждого импорта, а параллельные
     импорты компаний (`workers=8`) конфликтуют при слиянии атрибутов
     в общие EAN-страницы (lost updates) → 5 570 кодов товаров отсутствуют
     в каталожном слое.
2. **Генерация кода без валидации**: `generateCodeFromKey` / `slugify`
   принимают любой "ключ" (значение, предложение), не знают польскую диакритику
   (мапа `slugify` — только кириллица; `generateCodeFromKey` выкидывает
   всё, кроме `[a-z0-9_]`).
3. **`AttrDef.Categories` никогда не заполняется при импорте** — категорийная
   связь живёт только в производном индексе `attrdef_cat_codes`, а
   `GetCodesForCategoryTree` при пустых прямых кодах делает странное
   пересечение кодов дочерних категорий.
4. **Алиас-индекс `attrdef_key` пишется "на лету" при парсинге** и частично
   теряется (~8%) (нет атомарности с документом, нет пересборки) → дубли
   кодов при повторных импортах.
5. **Нет нормализации значений** (регистр, пробелы, единицы, списки) и
   **нет типов** — всё `string` (100% документов).
6. **Две параллельные модели**: `AttrDef` (живая) и `AttributeDefinition`
   (категорийная, с Options — мёртвая).
7. **`handleRemoveCategoryAttribute` сломан**: вычисляет `newCats`, но запись
   закомментирована — удаление атрибута из категории не сохраняется.
8. **JSON/Tradedoubler-импорт не парсит атрибуты из описаний** (только brand).
9. **Лимит 40 рун** применяется не во всех местах одинаково.

## 3. Целевая модель (простая, без новых сущностей)

Принцип: **один глобальный словарь кодов + категорийная привязка как данные,
а не как схема.** Никаких новых таблиц — только исправление существующих ключей.

```
┌─────────────────────────────────────────────────────────────────────┐
│ AttrDef (глобальный словарь, 1 документ на канонический код)        │
│   code        canonical: ^[a-z][a-z0-9]*(_[a-z0-9]+)*$, 3..40      │
│   name_ru/ua/pl/en   человекочитаемые имена (обязательно name_ru)   │
│   type        string | enum | multi_enum | int | float | bool | date│
│   unit        W | cm | kg | L | ... (для int/float)                │
│   keys[]      алиасы: сырые ключи, ведущие на этот код             │
│   is_active / is_filterable / is_sortable / sort_order             │
└─────────────────────────────────────────────────────────────────────┘
        │ 1..N                                   N
        ▼                                        ▼
┌───────────────────────┐            ┌────────────────────────────────┐
│ attrdef_cat_codes:{cat}│  (есть!)   │ attr_values_cat:{code}:{cat}   │
│ код в категории =      │            │ (есть!) наблюдаемые значения   │
│ "атрибут валиден для   │            │  категории = опции фильтра UI  │
│   категории"           │            └────────────────────────────────┘
└───────────────────────┘
```

Правила:

1. **Канонический код** — единственный источник. Сырой ключ из файла никогда
   не сохраняется как код напрямую: он проходит `Normalize → Resolve → Validate`.
2. **Категорийность = данные**: код "принадлежит" категории, если для пары
   (code, cat) есть данные (`attrdef_cat_codes` + `attr_values_cat`).
   Привязка создаётся автоматически при импорте (EAN-страница знает свою
   категорию) и управляется вручную в admin UI (`/admin/categories/{id}/attributes`).
3. **`AttrDef.Categories`** становится производным кэшем (union по
   `attrdef_cat_codes`) и синхронизируется при каждой пересборке — либо
   поле удаляется из модели.
4. **Типы**: `brand`, `kolor`, `materiał` и т.п. помечаются `enum`/`multi_enum`
   (опции = наблюдаемые значения из `attr_values_cat`), `moc`/`waga` —
   `float` + `unit`. Тип определяет нормализацию значения и виджет фильтра.
5. **Алиасы** (`keys[]` + `attrdef_key:`) — единственный способ, как сырой
   ключ попадает в код. Индекс пересобирается целиком из документов
   (идемпотентно), а не пишется "на лету".

## 4. Механизм парсинга и сохранения (pipeline)

### 4.1 Единое ядро (один мозг, много тонких адаптеров)

Все форматы сводятся к одному промежуточному виду — **сырым парам**:

```go
type RawAttr struct {
    Key   string // "Moc", "Moc - ", "MOCA"
    Value string // "500 W", "500W", "500 W (łącznie 25 W)"
    Src   string // "xml:property" | "html:table" | "html:li" | "text:line" | "json:field"
}
```

```
файл (XML/JSON/CSV/HTML)
   │
   ▼  [FormatAdapter — тонкий, стриминговый, без полного парса]
[]RawAttr
   │
   ▼  [Normalize — общее для всех форматов]
   │    trim, NBSP→space, схлопывание пробелов, "–/—/−"→"-",
   │    кавычки/тиры, html.Unescape, "×"→"x"
   ▼  [KeyCheck — это ключ или мусор?]
   │    2..40 символов, ≤4 слов, начинается с буквы, не из stop-list,
   │    не начинается с цифры, не содержит "в комплекте"-шум
   ▼  [Resolve — сырой ключ → канонический код]
   │    1) точный алиас (in-memory кэш attrdef_key, O(1))
   │    2) нормализованный алиас (lower, диакритика→ASCII, пробел→_)
   │    3) точное совпадение с кодом
   │    4) иначе: генерация канонического кода + регистрация алиаса
   │       (валидация: см. §5; если не проходит — пара отбрасывается в лог)
   ▼  [ValueNorm — по типу атрибута]
   │    enum/multi_enum: lower, trim, разбивка по ","/"и"/"or"
   │    float+unit:      извлечение числа и единицы ("5 W (łącznie 25 W)" → 5, W)
   │    string:          trim, ≤40 рун, отсечение хвостового мусора
   ▼  [Validate]
   │    value 1..40 рун, ≤6 слов, нет склейки (нет "lowerUPPER" в середине)
   ▼
[]model.KeyValue{code, value}   →  Product.Attributes
```

### 4.2 Адаптеры форматов (что уже есть, что добавить)

| Формат | Адаптер | Где живут атрибуты | Статус |
|---|---|---|---|
| Nokaut XML | `pricesrc.NokautParser` | `<property name="K">V</property>` + HTML-описание | есть, работает |
| HTML-таблица | `attrs.ParseTable` | `<tr><td>K</td><td>V</td></tr>` | есть, работает |
| HTML-список | `pricesrc.HTMLAttrKeyParser` | `<li>K - V</li>`, Nokaut-конкатенации | есть, работает (границы — см. §6) |
| Текст "Specyfikacja" | `pricesrc.HDWRAttrParser` | блок спецификации | есть |
| Простой текст | `pricesrc.ZabudowaAttrParser` | строки "K: V" | есть |
| JSON (Tradedoubler) | `import_json` | `brand`, `categories` + **описание** | есть, **описание не парсится — добавить** |
| CSV | новый, ~50 строк | колонки по заголовку | добавить (простейший) |

Все адаптеры вызывают **одно** ядро `attrs.Normalize + attrs.Resolve`.
Новый формат = новый тонкий адаптер (30–80 строк), без новых правил.

### 4.3 Сохранение в рамках категории

При импорте (без изменения текущих фаз):

1. Товар получает категорию (catalogizer — уже есть).
2. Пары (code, value) пишутся в `Product.Attributes` (как сейчас).
3. На EAN-странице (merge) индексируется **в связке с категорией**:
   - `eanpage_attr:{code}:{value}` — фильтрация (есть);
   - `attr_values_cat:{code}:{catID}` — опции UI (есть);
   - `attrdef_cat_codes:{catID}` — коды категории (есть);
   - **исправление**: `BatchUpsertCodes` делает **union** с существующим
     `attrdef_list`, а не перезапись;
   - **исправление**: после импорта один раз пересобирается
     `attrdef_key` из `keys[]` всех документов (идемпотентно);
   - **исправление**: `AttrDef.Categories` синхронизируется из
     `attrdef_cat_codes` (или поле удаляется).
4. Admin UI (`/admin/categories/{id}/attributes`) управляет привязкой:
   - POST code → `UpsertCode` + запись в `attrdef_cat_codes` (есть);
   - DELETE → **починить** `handleRemoveCategoryAttribute` (запись
     `newCats` сейчас закомментирована);
   - PATCH AttrDef (type/unit/names) → `HandleAdminAttrDefUpdate` (есть).

Итог: **"атрибут валиден для категории X" ≡ код есть в `attrdef_cat_codes:{X}`
и для него есть значения в `attr_values_cat:{code}:{X}`** — это уже то,
что показывает `GetCategoryAttrs` (фильтры каталога). Меняется только
надёжность наполнения этих индексов.

## 5. Правила валидности (жёсткие, в коде)

**Код** (`attrs.ValidCode`):
```
^[a-z][a-z0-9]*(_[a-z0-9]+)*$
длина 3..40, ≤4 слов, не начинается с цифры,
не в stop-list (zestaw, opis, cechy, ...),
не содержит 2+ подряд идущих "_"
```

**Ключ** (`attrs.ValidKey`) — до генерации кода:
```
2..40 символов, ≤4 слов, начинается с буквы (включая PL-диакритику),
не предложение (нет глагольных хвостов), не из noise-list
```

**Значение** (`attrs.ValidValue`):
```
1..40 рун, ≤6 слов,
нет склейки: нет перехода lower→UPPER внутри (кроме первых букв слов),
нет хвостового ". " + заглавная (начало следующего атрибута)
```

**Нормализация польской диакритики** (единая таблица, одна на всё):
```
ą→a ć→c ę→e ł→l ń→n ó→o ś→s ź→z ż→z   (и обратное не требуется)
```

## 6. План работ (от простого к сложному)

### Шаг 1. Пересборка/починка данных (одноразово, ~1 день)

Порядок важен — сначала каталожный слой, потом реестр:

1. **Пересборка EAN-страниц из товаров** (`BatchUpsertFromProducts` по всем
   товарам) — закрывает разрыв "5 570 кодов товаров нет в EAN-страницах".
   Заодно починить гонку: слияние атрибутов в общую EAN-страницу — под
   блокировкой по EAN (или единым пост-проходом после всех импортов);
2. **`attrdef_list`** ← union(текущий список ∪ коды из данных ∪ коды из
   документов);
3. **Merge дублей**: таблица алиасов (ручная, ~50 строк:
   `100_ochrona_uv → ochrona_uv`, `okadka → okladka`, ...) + применение
   к `Product.Attributes`/`EANPage.Attributes` + пересборка индексов;
4. **Удаление мусорных кодов**: коды-значения (начинаются с цифры, >4 слов,
   предложения) — пары переносить в родительский код, если очевиден
   (`10_cm` → `wymiary`), иначе удалять;
5. **Перегенерация кодов со сломанной диакритикой** (таблица §5);
6. Пересборка `attrdef_key` из `keys[]` всех документов;
7. Пересборка `attr_values_cat` + `attrdef_cat_codes` из EAN-страниц
   (готовое `RebuildAttrValuesFromEANPages`);
8. `ReindexProduct`/`ReindexEANPage` для затронутых документов.

Проверка: повторный `cmd/audit_attrs` → все метрики валидности зелёные.

### Шаг 2. Починка ядра (~1–2 дня)

1. `BatchUpsertCodes` — union вместо overwrite (3 строки);
2. `attrs.Normalize`/`Resolve`/`Validate` — единое ядро (§4.1) с тестами
   на реальных примерах из §1.7 (все найденные кривые случаи — в тесты);
3. `handleRemoveCategoryAttribute` — включить запись `newCats`;
4. `GetOrCreateByKey` — писать алиас атомарно с документом + использовать
   единый `Resolve`;
5. JSON/Tradedoubler импорт — прогнать описание через ядро (как в nokaut);
6. `GetCategoryAttrs` — убрать N-запросы `CountEANPagesWithAttrCode`
   (один батч-проход по `eanpage_attr_code` индексам или кэш).

### Шаг 3. Типы и нормализация значений (~1 день)

1. Пометить топ-коды типами (brand/kolor/materiał → enum, moc/waga/wymiary →
   float+unit) — скриптом по `attr_values_cat` (эвристика: >70% значений
   совпадают с числом+единицей → float+unit; ≤50 уникальных значений → enum);
2. `ValueNorm` по типу (извлечение числа+единицы, lower для enum);
3. Пересборка значений у EAN-страниц (одноразово) + индексов.

### Шаг 4. CSV-адаптер + документация (0.5 дня)

CSV: заголовок = ключи, строка = значения, `;`/`,` в значениях — в кавычках.
~50 строк поверх ядра.

## 7. Почему это "просто и быстро"

1. **Один мозг**: все форматы сводятся к `[]RawAttr` и проходят один
   `Normalize→Resolve→Validate`. Новый формат — тонкий адаптер без правил.
2. **Никаких новых сущностей/таблиц**: только существующие turbo/raw-ключи,
   которые уже работают (фильтры каталога, EAN-страницы, поиск).
3. **Стриминг**: все парсеры — токенизированные (XML/JSON), без загрузки
   файла в память (файлы до 400 МБ).
4. **O(1) резолв кода**: in-memory кэш алиасов (7–9 тыс. ключей ≈ 1 МБ),
   DB-хит только для нового ключа.
5. **Идемпотентность**: все пересборки индексов — чистые функции от данных
   (`Rebuild*` уже существуют), повторный запуск безопасен.
6. **Поэтапность**: каждый шаг проверяется `cmd/audit_attrs`
   (готов, отчёты в `_tmp/attr_audit.json`), и каждый даёт пользу сам по себе.

## 8. Внедрение без поломки существующего

### 8.1 Пять правил безопасности

1. **Бэкап до первого изменения** — база на диске 5.8 ГБ (sparse), копируется
   за минуты. Все дальнейшие шаги обратимы через бэкап.
2. **Сначала аддитивно, потом деструктивно** — сначала добавляем (union
   реестра, новые алиасы, новые индексы), проверяем, и только потом
   переименовываем/удаляем (merge дублей, мусорные коды).
3. **Каждый шаг идемпотентен** — повторный запуск безопасен; аудит
   (`cmd/audit_attrs`) — автоматические ворота между шагами.
4. **Офлайн-миграции** — makodb держит эксклюзивный lock на процесс:
   тяжёлые пересборки делаем с остановленным сервером (окно 2–4 часа),
   мелкие фиксы — кодом, без остановки.
5. **Новый парсер не меняет поведение на известных ключах** — алиас-хит
   возвращает тот же код, что и раньше; новая валидация применяется только
   к новым ключам. Регрессия на существующих данных исключена по
   конструкции.

### 8.2 Порядок внедрения (каждый этап — отдельный commit + аудит)

**Этап 0. Базовая линия (0.5 дня, без изменений данных)**

```bash
# 1. Бэкап (сервер можно не останавливать — copy-on-write не нужен,
#    но лучше в момент минимальной нагрузки):
cp -a makoshop_db makoshop_db.backup-$(date +%Y%m%d)

# 2. Базовый отчёт аудита (только чтение; если сервер работает —
#    остановим его, т.к. makodb = один процесс на БД):
go run ./cmd/audit_attrs -out _tmp/audit_before.json -probe3
```

Сохранить `_tmp/audit_before.json` — это эталон для сравнения после каждого
этапа. Критерий "не сломали": ни одна метрика не ухудшилась
(коды в данных ≥, покрытие `attr_values_cat` ≥, EAN-страницы с атрибутами ≥).

**Этап 1. Новый код, данные не трогаем (1–2 дня)**

Только аддитивные изменения, существующие пути не меняются:

1. `internal/attrs`: `Normalize`, `KeyCheck`, `Resolve`, `ValueNorm`,
   `Validate` + таблица польской диакритики. Чистые функции, без DB.
2. **Тесты на реальных кривых примерах из аудита** (все случаи §1.7 —
   тестовые векторы): `okładka→okladka`, `0.06 m³` (значение, не ключ),
   `jeepyFunkcje: warkot silnika` (склейка), `5 W (łącznie 25 W)` → `5`/`W`,
   `10-kolorowy długopis firmy Astra...` (предложение → отбросить).
3. `cmd/fix_attrs` с **dry-run по умолчанию**: читает БД, пишет план
   (`_tmp/fix_plan.json`: какие коды мерджнутся, какие удалятся, какие
   EAN-страницы пересоберутся), **ничего не меняет**.
4. `--apply` только после человеческого ревью плана (merge-таблица ~50 пар).

Проверка: `go build ./...`, `go test ./internal/attrs/...`, сервер работает
как раньше (код не затронут).

**Этап 2. Офлайн-миграция данных (окно 2–4 часа, сервер остановлен)**

Порядок жёсткий, после каждого подшага — аудит + запуск сервера на проверку:

```
A. Пересборка EAN-страниц из товаров (BatchUpsertFromProducts, готовый код)
   → закрывает разрыв 5 570 кодов; аудит: eanpage-коды ≈ product-коды
B. attrdef_list ← union(список ∪ данные ∪ документы)  [только добавление]
   → аудит: "data only (not in list)" → 0
C. Merge дублей по таблице (сначала upsert цели, потом миграция данных,
   потом пересборка индексов, потом удаление старых документов)
   → аудит: дублей нет, KV-пары не потеряны (сумма до/после)
D. Удаление мусорных кодов (начинаются с цифры / >4 слов / предложения)
   → аудит: "invalid format" → 0
E. Пересборка attrdef_key из keys[] всех документов  [идемпотентно]
F. RebuildAttrValuesFromEANPages (attr_values_cat + attrdef_cat_codes)
G. ReindexProduct/ReindexEANPage затронутых документов
```

Каждый подшаг `cmd/fix_attrs --stage=A..G --db makoshop_db` (по умолчанию
dry-run; `--apply` после ревью). Между подшагами: запуск сервера, проверка
каталога (чек-лист §8.4), остановка.

**Этап 3. Починка ядра кодом (1–2 дня, без остановки)**

Маленькие изолированные фиксы, каждый — отдельный commit:

1. `handleRemoveCategoryAttribute` — включить запись `newCats` (3 строки);
2. `GetOrCreateByKey`/`BatchGetOrCreateByKeys` — алиас атомарно с документом
   + единый `Resolve` из `internal/attrs`;
3. `GetCategoryAttrs` — батч-счётчики вместо N-запросов (кэш уже есть);
4. JSON/Tradedoubler импорт — описание через ядро (флаг `MAKOSHOP_ATTR_HTML=1`,
   по умолчанию off → включаем после проверки на одном файле);
5. Гонка импортов: слияние атрибутов в EAN-страницу — единым пост-проходом
   после всех компаний (не внутри параллельных воркеров).

**Этап 4. Типы и нормализация (1 день, опционально по кодам)**

1. Пометить типы: сначала `brand` (286 тыс. пар), потом топ-20 по данным —
   скриптом по `attr_values_cat` (эвристика §6 шаг 3);
2. `ValueNorm` по типу + одноразовая пересборка значений (dry-run → ревью →
   apply);
3. CSV-адаптер (50 строк поверх ядра).

### 8.3 Гарантии против дублей в индексах

Проверено по исходникам makodb и текущему коду:

| Индекс | Хранение | Дубли |
|---|---|---|
| `attrdef_cats`, `eanpage_attr`, `eanpage_attr_code`, `product_list`, `eanpage_list` | turbo (отсортированное множество) | **невозможны**: `turboPutIndex` — binary search, повторный put того же docID игнорируется |
| `attrdef_key:{rawkey}`, `attrdef_code:{code}` | raw-ключ → одно значение | невозможны (overwrite) |
| `attr_values_cat:{code}:{catID}` | JSON-мап `{value: true}` | невозможны (overwrite) |
| `attrdef_list`, `attrdef_cat_codes:{catID}` | JSON-массив | **возможны при append'е** — см. правила ниже |

Правила записи (обязательны для всего нового кода):

1. **JSON-массивные индексы пишутся только как полный set одним write**
   (пересборка) либо через дедуп-хелперы `addToAttrDefList` /
   `addToCatCodes` (проверка перед append). Никакого слепого append.
2. **Починить `BatchGetOrCreateByKeys`**: финальная запись `attrdef_list`
   сейчас `append(existing, newCodes)` без проверки — заменить на
   set-union с дедупликацией.
3. **Один документ на код**: `Resolve` создаёт документ только после
   проверки (1) in-memory кэша, (2) `attrdef_code:{code}`. Пара
   "doc + индекс" пишется одной операцией; осиротевший документ
   (крах между двумя записями) безвреден — он нигде не читается.
4. **Аудит проверяет дубли**: дубли в `attrdef_list`, дубли кодов в
   `attrdef_cat_codes`, дубли (code, value) в документах — метрики в
   отчёте, цель = 0.

### 8.4 Чего НЕ делать

- Не менять формат turbo-индексов и имена ключей (`attrdef_list`,
  `attr_values_cat:...`) — от них зависят поиск и UI;
- Не делать "большой баг-бэнг": не переписывать всё за один проход;
- Не менять `mergeAttributes` (проверенный код, на нём держатся EAN-страницы);
- Не трогать `eanpage_attr` во время импорта (только в оффлайн-окне);
- Не удалять AttrDef-документы до пересборки всех индексов (сироты);
- Не запускать миграции при работающем сервере (lock makodb).

### 8.6 Откат

- Любая ошибка до конца этапа 2 → `rm -rf makoshop_db && mv makoshop_db.backup-* makoshop_db`;
- Ошибка на этапе 3 (код) → revert commit, данные не пострадали
  (этапы 3–4 не меняют данные без dry-run/apply);
- Бэкап держать до первого успешного полного цикла импорта после миграции.

### 8.7 Защита от раздувания БД (append-only, без компрессии в работе)

makodb — append-only: каждая перезапись того же ключа **резервирует новое место**,
старое не освобождается до вакуума (само-компрессия происходит **на старте** сервера).
Поэтому в работе недопустимо многократно переписывать один и тот же ключ — это
раздувает `FreeOffset` и приводит к `out of database space`.

Правило: **каждый общий ключ записывать максимум 1 раз на импорт** (батч-запись).

Что сделано (все изменения — батчевые):

| Ключ | Было | Стало |
|------|------|-------|
| `attrdef_list` | перезапись на каждый созданный AttrDef (~13 000×/импорт ≈ 1.3 ГБ) | буфер `pendingListCodes` + `FlushList()` — **1 запись** на батч/импорт |
| `attrdef_cat_codes:{catID}` | перезапись на каждый (code, cat) | `mergeCatCodes(catID, set)` — **1 запись** на категорию |
| turbo-индексы (`product_list`, `eanpage_list`, price, brand, …) | — | уже батчевые через транзакцию (`TurboPutBatchIndexString` при коммите) |
| fallback `GetByCode` (doc без записи в списке) | doc создавался без регистрации | `addPendingListCode(code)` — попадает в `FlushList()` |

Разовый ремонт осиротевших doc: `go run ./cmd/attrs_heal` (добавляет все коды
документов в `attrdef_list` одной записью; идемпотентно, сервер остановлен).

Результат: полный импорт (9 компаний, ~440 000 товаров) раздвинул БД лишь на
~0.6 ГБ (6.0 → 6.6 ГБ), ошибок `out of space` нет; на старте сервер само-сжимает
остатки (8.7 → 6.0 ГБ в одном цикле).
